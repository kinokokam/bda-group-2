Big Data final project · Business Question 2 · IBM AML HI-Small

Where does money laundering concentrate, and how does each scheme move money?

A plan for answering one question well: map where laundering piles up across payment channels, currencies, banks and amounts, and profile the eight laundering schemes, using the cheapest AWS pipeline that still processes all 5 million transfers.

a · Problem statement

Banks look everywhere equally, but laundering does not spread out evenly

  1. Banks process millions of transfers a day and only about 1 in 1,000 is laundering, so checking everything the same way wastes most of the effort.
  2. Limits and checks are usually set the same for every payment channel, currency and partner bank, without evidence of where the risk actually sits.
  3. Launderers reuse a few recognisable schemes (fan-out, cycle, stack and others) spread over many accounts and banks, which you cannot see by looking at one transfer at a time.
  4. Amounts arrive in 15 currencies, so nobody can fairly compare how much money is at risk in each channel or route until everything is in one currency.
  5. We need a cheap, repeatable pipeline that turns 5 million raw transfers into a clear map of where laundering concentrates and which schemes are hardest to catch.
b · What we have done so far

Exploratory analysis on the real file already shows strong concentration

We downloaded HI-Small from Kaggle, ran our profiling script (profile_aml.py) over every row, and trained a quick gradient-boosted tree model. Five findings shape the rest of the plan:

  • One channel dominates. ACH is 11.8% of transfers but 86.6% of laundering. Wire and Reinvestment have none at all.
  • A short list of banks. 89 of 30,470 sending banks (0.3%) account for half of all laundering transfers. Individual bank-to-bank routes are spread thin: the top 10 routes carry only 2.9%.
  • Launderers stay in one currency. 98% of laundering crosses banks, yet none of the 72,170 currency-conversion transfers is laundering. Saudi Riyal payments launder at 4.1× the average rate.
  • Mid-sized amounts. 72% of laundering transfers are 1,000–50,000 in the payer's currency; the 10,000–50,000 band carries 2.5× its fair share.
  • Schemes behave differently. Gather-scatter schemes run about six days across 15 accounts; bipartite schemes finish in a day. After 10 Sep the data is almost all laundering tail-ends, so we leave 11–18 Sep out.
c · End goal and who benefits

A laundering exposure map that tells each team where to act first

  • Which channels, currencies, banks and amount bands carry more than their fair share of laundering (measured in US dollars).
  • How each of the eight schemes moves money (hops, accounts, hours, dollars per hop).
  • Which schemes are hardest to catch.

Architecture

Seven steps, one S3 bucket, nothing to switch off

Every piece is pay-per-use: S3 stores, Lambda runs small Python jobs, Athena does the heavy SQL over all 5 million rows, and Apache Airflow on a laptop runs the chain. XGBoost runs in our own Jupyter notebook, so the model step costs nothing. No cluster, no database, no paid dashboard or scheduler service.

Each Athena table points at a folder, so every file gets its own folder.

Parquet is a file format that stores a table column by column and compresses it. A query that needs 3 of 20 columns reads only those 3, so Athena scans (and bills) far less than with CSV.
Partition means splitting the table into one folder per date (txn_date=2022-09-01/ and so on). A query filtered to certain dates only opens those folders.

Show the key SQL (table definition, clean-and-enrich, one mart) 
-- Step 4a · point Athena at the raw CSV (hand-written DDL, so no Glue crawler cost)
CREATE EXTERNAL TABLE raw_trans (
  ts string, from_bank string, from_account string, to_bank string, to_account string,
  amount_received double, receiving_currency string, amount_paid double,
  payment_currency string, payment_format string, is_laundering int)
ROW FORMAT DELIMITED FIELDS TERMINATED BY ','
LOCATION 's3://aml-bq2-<team>/raw/trans/'
TBLPROPERTIES ('skip.header.line.count'='1');
-- Step 4b · clean, convert to USD, attach scheme labels, write Parquet by date
CREATE TABLE curated_transactions
WITH (format = 'PARQUET', write_compression = 'SNAPPY',
      external_location = 's3://aml-bq2-<team>/curated/transactions/',
      partitioned_by = ARRAY['txn_date']) AS
WITH t AS (SELECT DISTINCT * FROM raw_trans)
SELECT
  date_parse(t.ts, '%Y/%m/%d %H:%i')                        AS ts,
  hour(date_parse(t.ts, '%Y/%m/%d %H:%i'))                  AS txn_hour,
  t.from_bank, t.from_account, t.to_bank, t.to_account,
  t.payment_format, t.payment_currency, t.receiving_currency,
  t.amount_paid,
  t.amount_paid / fx.units_per_usd                          AS amount_paid_usd,
  t.is_laundering,
  IF(t.from_bank <> t.to_bank, 1, 0)                        AS is_cross_bank,
  IF(t.payment_currency <> t.receiving_currency, 1, 0)      AS is_cross_currency,
  COALESCE(p.pattern, IF(t.is_laundering = 1, 'UNSTRUCTURED', 'NONE')) AS pattern,
  p.attempt_id, cl.country, cl.basel_score,
  date_format(date_parse(t.ts, '%Y/%m/%d %H:%i'), '%Y-%m-%d') AS txn_date
FROM t
JOIN currency_lookup cl ON cl.currency_name = t.payment_currency
JOIN fx_rates fx        ON fx.iso_code = cl.iso_code
                       AND fx.rate_date = substr(t.ts, 1, 10)
LEFT JOIN patterns p    ON p.ts = t.ts AND p.from_account = t.from_account
                       AND p.to_account = t.to_account AND p.amount_paid = t.amount_paid;
-- fx_rates.rate_date is stored as 'YYYY/MM/DD' text to match the raw timestamp prefix
-- Step 5 · one mart: lift by payment format (laundering share ÷ transfer share)
CREATE TABLE mart_channel_lift
WITH (format = 'PARQUET', external_location = 's3://aml-bq2-<team>/marts/channel_lift/') AS
SELECT payment_format,
       count(*)                                              AS txns,
       sum(is_laundering)                                    AS laundering_txns,
       sum(amount_paid_usd) FILTER (WHERE is_laundering = 1) AS laundering_usd,
       (sum(is_laundering) * 1.0 / sum(sum(is_laundering)) OVER ())
         / (count(*) * 1.0 / sum(count(*)) OVER ())          AS lift
FROM curated_transactions
WHERE txn_date <= '2022-09-10'
GROUP BY payment_format;
Step 6 in detail

The XGBoost analysis, from our first run to the AWS version

What goes in

  • Rows: curated_transactions for 1–10 Sep, joined to curated_accounts.
  • About 21 features: payment format, currency, USD amount and its log, hour, weekday, night and weekend flags, round-amount and just-under-10,000 flags, cross-bank, cross-currency, self-transfer, sender fan-out degree, receiver fan-in degree, same-day sender and receiver counts, pass-through ratio.
  • Never as inputs: is_laundering, pattern, attempt_id. The pattern is only used afterwards to group results.
  • Split by time: train 1–7 Sep (3,731,669 rows, 3,027 laundering), test 8–10 Sep. A random split would leak account behaviour from the future.

Settings and outputs

  • Model settings: scale_pos_weight = negatives ÷ positives (≈ 1,232 here), shallow trees, eval_metric='aucpr', tree_method='hist'. Tune on PR-AUC, not recall.
  • Outputs to marts/model/: feature importance, SHAP summary, detection rate per scheme at a 0.5% alert budget, summed risk score per channel, currency and bank.
  • Baseline to beat: F1 0.34, PR-AUC 0.31. The dataset authors report F1 0.63 with graph features, so adding fan-in / fan-out and scheme-shape counts is the main lever.
  • Where it runs: your own Jupyter notebook. aws s3 sync s3://aml-bq2-<team>/curated/ ./curated/ pulls the data down, pip install xgboost shap pyarrow covers the libraries, and pd.read_parquet("curated/transactions") reads every date folder at once. Loading 5 million rows needs about 3 GB of RAM. When done, aws s3 cp the output CSVs to marts/model/.

What we dropped and why

  • Glue ETL job: $0.44 per DPU-hour and a Spark script to debug. Athena CTAS does the same clean-up for about a cent. If the course insists on Spark, step 4 swaps to a Glue job running the same logic.
  • Glue crawler: replaced by the hand-written CREATE TABLE above.
  • EMR cluster: pays by the hour even when idle; our data fits Athena comfortably.
  • Redshift, RDS, QuickSight: excluded by the brief.
  • Managed Airflow (MWAA): about $0.49 an hour for the smallest environment, roughly $350 a month. The same Airflow runs free in Docker on a laptop.
  • Managed Grafana: needs IAM Identity Center, which shared course accounts often block, and costs $9 per editor after the trial. A static Plotly page on S3 costs nothing.

What it adds

From a one-off report to a live feed that is checked and explained

The batch pipeline answers BQ2 once, for 1–10 Sep. The monitoring layer replays the same data one hour at a time, checks every slice before it can reach the dashboard, and has a Claude agent write down what changed and whether it matters. The exposure map stays current and trustworthy, and a person reads a short verdict instead of a table of test results.

Why it matters

Three problems it would catch in our own data

These are measured on HI-Small, not made up. Each one would quietly distort the BQ2 answer if the pipeline ran without checks.

CheckWhat is in the dataWithout the checkWith the check and the agent
Reconciliation The ECB publishes no FX rates at weekends. The three weekend days (3, 4 and 10 Sep) hold 12% of transfers but 27% of laundering (1,240 of 4,522). A plain join to FX silently drops those 623,137 rows. ACH and Saudi Riyal look less risky than they are, and nobody notices. Rows and dollars in ≠ rows and dollars out, so the run stops. The agent's note names the cause: all missing rows fall on Saturday or Sunday.
Drift, expected On 1 Sep, 43% of transfers are Reinvestment and 344,208 land at midnight. On every other day Reinvestment is 0%. Payment-format PSI is 3.9 against a normal weekday. A fixed threshold fires every month-start. People soon learn to ignore the alerts. The drift check flags it; the agent looks at which category moved and when, and rates it low: a month-start batch, not new behaviour.
Anomaly, real From 11 Sep every transfer is ACH and 57–73% are laundering, against 0.10% normally. Volume falls from about 482,000 a weekday to a few hundred. Payment-format PSI is 8.8. The dashboard shows ACH laundering exploding, and a model trained on it learns that late September means laundering. The slice is quarantined and kept out of the marts and model training. The agent explains it as the simulator's leftover laundering hops.

The second row is where the AI earns its place. A threshold only knows that a number is large; the agent reads the context (which category, what time, what day of the month) and separates a routine event from a real shift. That is the judgment a human analyst would otherwise make by hand for every alert.

The agent

LangChain + Claude, kept on a short leash

  • Runs as: an Airflow Python task using LangChain with Claude, via Amazon Bedrock if the course account allows it, otherwise the Anthropic API.
  • Reads: the slice's check results (numbers only).
  • Tools: run_saved_query (five fixed, read-only Athena queries), get_baseline, get_top_alerts. At most three tool calls per slice.
  • Writes: structured JSON with severity, verdict (expected / investigate / data issue), a three-sentence summary, the numbers it used, and a suggested action.
  • Guardrails: no free-form SQL, no writes, a token cap per call, and a check that every number in the note appears in a tool result. The gate is decided by code, never by the agent.
